Each service in the backend is organized as per feature. 
- `service.go` - The business logic of the service
- `handler.go` - The handlers that will be given to the server

Don't create a file to store the types that will be returned by the request. That type is most likely generated by `sqlc` already.

In the event that you need another type (i.e. a new structure), keep it close to the function that returns it.

Always pass in the context to functions in the service

Example Structure:
```go
// users/handler.go
var (
    ErrorAuthFailed = errors.New("Failed to auth")
)

type UserHandler struct {
    users *UserService
    auth  *AuthService // Obtained using dependency injection
}

// Handles the "GET /user/profile/" endpoint
func (h *UserHandler) profile(w http.ResponseWriter, r *http.Response) {
    ctx := r.Context() 
    
    h.auth.AuthUser(ctx)  // from auth/service.go
    h.svc.GetUserProfile(ctx)
    h.svc.GetUserPosts(ctx)
    h.svc.GetUserWhirlpool(ctx)
}

// users/service.go
type UserService struct {}

// Profile is found in database/
func (s *UserService) GetUserProfile(ctx context.Context) (Profile, error) {}
func (s *UserService) GetUserPosts(ctx context.Context) (Post, error) {}

// Returns a `Whirlpool` struct. This is not generated by sqlc. 
type Whirlpool struct {
    whirling    bool
    user        int64
}

func (s *UserService) GetUserWhirlpool(ctx context.Context) (Whirlpool, error) {}
```

# Rules
- One service is one feature. Avoid separating services when they can be grouped together as one feature
    ```
    BAD: Dependency management gets really messy when doing this
    users/
        profile/
            handler.go
            service.go
        auth/
            handler.go
            service.go
        posts/
            handler.go
            service.go
    GOOD: 
        handler.go
        service.go
    ```

- Services should only be given dependencies that is required to fulfill the task. 
    ```go
    // Bad: UserService only needs the database to query the user
    type UserService struct {
        database    Database 
        timer       Timer
    }
    // Good
    type UserService struct {
        database    Database 
    }
    ```
- Avoid overlapping use cases whenever possible
    
    If two services have functions that are similar, it means that one of the services is dependent on the other.
    
    If the service only has one dependency and their domains are similar, combine them into one service instead
    
    ```go
    // Bad: Duplication of code
    type UserService struct{}
    type AuthService struct{}
    
    func (s *AuthService) authUser(ctx context.Context) error {}
    func (s *UserService) authUser(ctx context.Context) error {}
    
    // Good: Combine the AuthService with the UserService as UserService is the only consumer of AuthService
    type UserService struct{}
    func (s *UserService) authUser(ctx context.Context) error {}
    ```
    
    If a multiple services depend on one service or in cases where their domains are too distant, add a pointer to the dependent service to the child services instead
    ```go
    type AuthService struct{}
    type UserService struct{
        auth    *AuthService
    }
    type AdminService struct{
        auth    *AuthService
    }
    
    func (s *AuthService) authUser(ctx context.Context) error {}
    ```

- Always return an error type unless it's trivial that the function in the service will never fail
    ```go
    // Bad: Database connection could fail and the handler will not know why
    func (s *AuthService) AuthUser(ctx context.Context) bool {}
    
    // Good
    func (s *AuthService) AuthUser(ctx context.Context) (bool, error) {}

    // Passable but not preferable. 
    func (s *AuthService) PrintUsername(ctx context.Context) {}
    ```

    Error types must always be defined in the service's `handler.go` file. Avoid returning raw `errors.New()`
    
    ```go
    // some/handler.go
    var (
        ErrorMyError = errors.New("My new error")
    )
    ```
